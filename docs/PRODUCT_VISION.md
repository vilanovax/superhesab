# SuperHesab — Product Vision

> سند مرجع برای مسیر توسعه در Cursor. هر تغییر اسکوپ باید با این سند هم‌راستا باشد.

## تعریف دقیق پروژه

این پروژه یک **اپلیکیشن مدیریت مالی چند-کاربره و مبتنی بر قالب (Template-Driven)** است که به عنوان یک **PWA** با **Next.js** توسعه می‌یابد.

**ارزش اصلی (Core Value):** یکپارچه‌سازی نیازهای مختلف مالی گروهی و شخصی در یک هسته واحد.

به جای دیتابیس یا موتور جدا برای هر نوع حساب‌وکتاب، یک **موتور مرکزی** ساخته می‌شود:

| لایه هسته | مسئولیت |
|-----------|---------|
| Spaces | ظرف چندکاربره برای یک «حساب‌وکتاب» |
| Expenses + Splits | ثبت هزینه و تسهیم |
| Settlements | ساده‌سازی بدهی و تسویه دستی |
| Membership / RBAC | نقش و دسترسی |

«قالب‌ها» (Templates) **داده‌مدل موازی نمی‌سازند**؛ فقط:

- نحوه نمایش UI
- سیاست‌های پیش‌فرض دسترسی
- فیلدها / جریان‌های اختیاری قالب‌محور

را تغییر می‌دهند.

### اصل معماری که نباید نقض شود

ساختار باید طوری باشد که برای ساخت تمپلیت بعدی **دست بسته نباشد**. هسته ثابت می‌ماند؛ تمپلیت‌ها قابل گسترش و اختیاری‌اند.

```
┌─────────────────────────────────────────────┐
│  Template Layer (UI + policies + extras)    │
│  Trip | Partner | Personal | Building (v2)  │
├─────────────────────────────────────────────┤
│  Core Engine (shared, stable)               │
│  Space · Member · Expense · Split · Settle  │
└─────────────────────────────────────────────┘
```

## فازبندی توسعه محصول

### فاز اول — MVP

**هدف:** پیاده‌سازی هسته مرکزی و اعتبارسنجی پیچیده‌ترین بخش معماری (موتور تسویه + مدیریت فضاها).

| حوزه | محدوده MVP |
|------|------------|
| احراز هویت | ورود سریع (Magic Link / Google) |
| فضاها | ساخت Space، دعوت با لینک |
| هزینه | فرم ثبت هزینه سریع |
| تسهیم (Split) | فقط **مساوی** و **مبلغ دقیق دستی** |
| تسویه | الگوریتم **Debt Simplification** + تایید دستی |
| ابزار جانبی | چک‌لیست اشتراکی (نزدیک به بلادرنگ) |
| قالب‌های فعال | **سفر و دورهمی** · **حساب دونفره / پارتنر** · **حسابداری شخصی** · **خانواده** |

**خارج از اسکوپ MVP:** شارژ ماهانه ساختمان، تسهیم درصدی، آپلود فاکتور، داشبورد گرافیکی / Excel / PDF.

### فاز دوم — v2 (مقیاس و قالب‌های پیچیده)

پس از پایداری هسته:

- **قالب مدیریت ساختمان:** شارژ ماهانه، موجودیت «واحد» به‌جای «شخص»، نقش **Viewer**
- **تسهیم پیشرفته:** درصدی
- **اسناد:** آپلود و الصاق عکس فاکتور به هزینه
- **گزارش:** داشبورد گرافیکی، خروجی Excel / PDF

## اولین تمپلیت: سفر و دورهمی (Trip & Party)

انتخاب این تمپلیت به‌عنوان اول، چون اگر موتور بتواند دنگ‌های نامنظم یک سفر شلوغ را حل کند، بقیه قالب‌ها ساده‌تر می‌شوند.

### خصوصیات

| موضوع | تعریف |
|-------|--------|
| ماهیت تراکنش‌ها | مقطعی، نامنظم، به‌شدت نیازمند تسهیم |
| RBAC پیش‌فرض | سازنده = **Owner**؛ دعوت‌شدگان با لینک = **Editor** (ثبت هزینه + تغییر چک‌لیست) |
| Expense Flow | تعیین **Paid By** → تعیین افراد مشمول و فرمول (**equal** یا **exact amounts**) |
| داشبورد ترازنامه | تمرکز روی **Net Balance** هر نفر (طلبکار / بدهکار کل سفر) بدون درگیر کردن کاربر در ریز زنجیره بدهی‌ها |
| تسویه هوشمند | پیشنهاد مسیر بهینه تسویه (کاهش تعداد تراکنش‌ها) |
| چک‌لیست مشارکتی | لیست ساده برای هماهنگی قبل/حین سفر (خرید، وظایف) |

### معیار موفقیت تمپلیت Trip

1. کاربر در کمتر از ۳۰ ثانیه بفهمد «من چقدر بدهکارم / طلبکارم».
2. تسویه پیشنهادی سیستم با تایید دستی قابل ثبت باشد.
3. چند Editor هم‌زمان بتوانند هزینه و چک‌لیست را بدون قفل شدن هسته ویرایش کنند.

## تمپلیت دوم MVP: حساب دونفره / پارتنر (Partner)

همان هسته؛ تفاوت عمدتاً در UX و فرض دو نفره:

- فضای کوچک (معمولاً ۲ عضو)
- همان Split و Settlement
- دعوت و نقش مشابه (Owner + Editor)

جزئیات UI پارتنر بعد از پایدار شدن Trip تکمیل می‌شود؛ **هیچ schema جداگانه‌ای** برای Partner ساخته نمی‌شود مگر فیلد `Space.type = PARTNER`.

---

## تمپلیت: حسابداری شخصی (Personal)

همان هسته Expense؛ تفاوت در UX تک‌نفره و جریان درآمد/هزینه:

- `Space.type = PERSONAL` — فقط یک عضو (مالک)، بدون دعوت
- `Expense.transactionType` = `EXPENSE` | `INCOME`
- `Space.monthlyBudget` — سقف هزینه ماهانه (اختیاری)
- UI: داشبورد ماه + گزارش دسته؛ بدون تسویه / چک‌لیست / اعضا
- ماژول **بدهی و طلب** (`debts: true`) — جدا از Expense؛ جزئیات: [`docs/debt-module-prd.md`](./debt-module-prd.md)
- عمق Personal: بودجه per-category، run-rate، تراکنش تکرارپذیر — [`docs/personal-depth-prd.md`](./personal-depth-prd.md)

---

## تمپلیت: خانواده (Family)

لجر مشترک خانوار **بدون تسویه بین اعضا**. جزئیات کامل: [`docs/family-template-prd.md`](./family-template-prd.md).

- `Space.type = FAMILY` — ۲ تا ۸ عضو؛ دعوت با نقش EDITOR/VIEWER
- `incomeExpense` + `budget` + `householdLedger`؛ `settlements: false`
- `debts: true` — وام/اقساط بیرونی (جدا از Expense)؛ جزئیات: [`docs/debt-module-prd.md`](./debt-module-prd.md)
- Paid By بین اعضا؛ بدون Split UI؛ EDITOR فقط تراکنش Expense خودش را ویرایش می‌کند

---

## تمپلیت: ساختمان (Building) — v2

مدیریت شارژ و هزینه مشاع آپارتمان. جزئیات: [`docs/building-template-prd.md`](./building-template-prd.md).

- `Space.type = BUILDING` — واحدها، پلن شارژ سالانه، وصول شارژ (جداول additive)
- `settlements: false` · `debts: false` · هزینه مشاع روی `Expense`
- بدهی واحد پویا محاسبه می‌شود؛ ماه‌ها pre-allocate نمی‌شوند

---

## تمپلیت: صندوق نوبتی (Fund) — فاز A

صندوق قرض‌الحسنه / ROSCA. جزئیات: [`docs/fund-template-prd.md`](./fund-template-prd.md).

- `Space.type = FUND` — پلن سهم، نوبت دستی، تیک وصول (جداول additive: `FundPlan` / `FundTurn` / `FundPayment`)
- `fundRotating: true` · `invites: true` · بدون Expense / Settlement / Debt
- سهم اعضا: `SpaceMember.defaultShare` (half-units، Int)
- فاز B: قرعه / فیش / پرتال عضو — بعدی

## واژه‌نامه

| اصطلاح | معنی |
|--------|------|
| Space | یک فضای حساب‌وکتاب اشتراکی |
| Template | لایه نمایش و سیاست روی Space، نه دیتابیس جدا |
| Net Balance | مانده خالص یک کاربر در یک Space |
| Debt Simplification | کاهش گراف بدهی به حداقل تراکنش‌های تسویه |
| Editor | عضو با حق ثبت/ویرایش هزینه و چک‌لیست |
| Owner | سازنده؛ مدیریت اعضا و تنظیمات فضا |
